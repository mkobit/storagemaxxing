## Context

`.github/workflows/ci.yml` (post sm-nrbu) runs `lint`, `typecheck`, `test`, `build-storybook`, `e2e` as independent jobs. `test` passes `--coverage` on both invocations (sm-wghm) for visibility only — no threshold, no failure on regression. There is no dead-code step. `eslint.config.ts` already uses `eslint-plugin-import-x`'s `no-restricted-imports` to ban barrel imports (lines 33, 115) but has no rule constraining `eslint-disable` comment hygiene.

## Decision 1: Dead-code tool — knip, chosen from real comparative runs

All three candidates were run against this exact repo (not evaluated on paper):

**`bunx knip`** (zero-config): monorepo-package-aware — correctly attributed the unused `@storagemaxxing/packer` dependency to both `apps/web/package.json:26:6` and `packages/assembly/package.json:12:6` independently, i.e. it resolves each workspace package's own dependency graph rather than flattening the repo into one graph. Reported in structured sections: unused files (7), unused deps (2), unused devDeps (7), unused exports (35), unused exported types (24), duplicate exports (4). The "unused files" list includes `.agents/hooks/*.ts` (6 files) and `apps/web/e2e/fixtures/catalogWithDrillFixture.ts` — both false positives under zero-config, but for reasons knip's config surface directly targets: hooks are harness entry points, not import-graph nodes, and the e2e fixture is only reachable through a runtime-conditional Vite alias (`E2E_DRILL_FIXTURE=true` in `apps/web/vite.config.ts`). Both are exactly what knip's `entry`/`ignore` config exists to declare — see spec.md's "Known dynamic-resolution patterns" scenario. **Correction from independent review**: of the 6 flagged hook files, only 5 are actual harness entry points — the 6th, `.agents/hooks/claude-hook.ts`, is a shared helper imported by the other 5 (`import { readHookInput } from "./claude-hook"`) and only appears unused because none of its importers are themselves reachable from knip's default entry inference. `knip.json`'s entry list should name the 5 harness-invoked scripts (the ones literally referenced in `.claude/settings.json`'s hooks config: `lint-on-edit.ts`, `typecheck-on-edit.ts`, `openspec-validate-on-edit.ts`, `openspec-canonical-guard-on-edit.ts`, `git-commit-main-guard.ts`) — `claude-hook.ts` then resolves as used transitively and needs no separate entry/ignore declaration of its own.

**`bunx ts-prune`**: exports-only — no dependency-level detection at all (would miss the `@storagemaxxing/packer` finding entirely), no file-level dead-file detection, and noisier: every export used only within its own declaring module is still listed, tagged `(used in module)`, forcing a manual second read to distinguish genuinely-dead exports from merely-not-re-exported ones. No monorepo package-boundary awareness demonstrated in the output (flat list across all packages, unattributed to which package.json a finding belongs to).

**`bunx depcheck`**: dependency-only, and only against the *root* `package.json` by default — it did not surface the `packages/assembly`-scoped `@storagemaxxing/packer` finding knip caught, because it isn't workspace-aware out of the box. It also produced two clear false positives from its own limitations: flagged `bun:test` as a "missing dependency" (a Bun built-in, not an npm package) and flagged `@fission-ai/openspec`/`prettier-plugin-packagejson` as unused despite both being invoked via `bunx`/CLI rather than imported (the exact class of agent-tooling-only package AGENTS.md's "Agent Tooling Packages" section already carves out of the import graph deliberately).

**Verdict**: knip is the only one of the three that is both monorepo-package-aware and does full-spectrum detection (files + deps + exports + types) in one pass. It requires the most upfront config work (entry points for hooks, ignore pattern for the aliased e2e fixture, and marking `@fission-ai/openspec`/`prettier-plugin-packagejson`/`modern-web-guidance` as CLI-only per AGENTS.md's existing carve-out) but that cost is paid once, in `knip.json`, not per-PR. Wired as a new step inside the existing `lint` CI job (not a new job) — it's a static analysis check with the same trigger conditions as ESLint, and splitting it into its own job would add a redundant checkout/mise/install cycle for a step that runs in seconds.

## Decision 2: Coverage threshold — `bunfig.toml`'s `test.coverageThreshold`, verified real, baselines measured live

Confirmed against this repo's installed `bun-types` package (`node_modules/bun-types/docs/test/code-coverage.mdx`), not assumed: `[test] coverageThreshold` is a real, documented Bun config field, settable as a single number (applies to both `functions` and `lines`) or a table (`{ line = 0.7, function = 0.8 }`). `coveragePathIgnorePatterns` (also real, same doc) excludes matched files from the coverage calculation entirely — the right mechanism for `packages/geometry/src/testing.ts`, a test-factory module that imports `bun:test` and would otherwise drag its own partial internal coverage into the gate for unrelated product-code changes.

Measured baselines, run live via the exact CI commands:

| Invocation | Command | Measured % Funcs | Measured % Lines |
|---|---|---|---|
| packages + hooks | `bun test packages ./.agents/hooks --coverage` | 91.67 | 97.41 |
| apps/web | `bun --cwd apps/web test src --coverage` | 86.33 | 91.87 |

Proposed thresholds, **widened from the original buffer after independent review found it was too tight to serve its own stated purpose**: a live re-measurement estimated the original 1.3-1.7-percentage-point margins on functions translate to roughly 2-5 individual functions of headroom at this repo's current function counts (~150-165 for packages+hooks, ~295 for web) — a single ordinary PR adding a handful of untested pure functions could plausibly trip the gate, which is exactly the "tripwire on every PR" outcome the buffer was meant to prevent:

- Root `bunfig.toml` (packages + hooks): `coverageThreshold = { line = 0.90, function = 0.85 }` (was `0.95`/`0.90` — now a ~7-12 point margin below measured, not ~1.5-2)
- `apps/web/bunfig.toml`: `coverageThreshold = { line = 0.85, function = 0.80 }` (was `0.90`/`0.85` — same widening)

These wider values are a starting point, not re-derived from a function-count model — the implementation bead should re-measure immediately before shipping (baselines drift as the repo changes) and treat "does a normal small PR trip this" as the acceptance bar, not just "is it below today's snapshot."

Bun's own coverage report already breaks numbers down per-file (confirmed in the raw `bun test --coverage` output: e.g. `packages/geometry/src/Dimensions2D.ts` sits at 0% funcs / 58.33% lines today, dragged down by an apparently-untested branch), but `coverageThreshold` in `bunfig.toml` is a single value applied to the whole invocation, not configurable per-file or per-package within one invocation — this is a real Bun limitation, not a design choice. A genuinely per-package gate (e.g. `packages/geometry` at a stricter bar than `apps/web`) would require either separate `bun test` invocations per package with their own `bunfig.toml` (a bigger CI restructure, out of scope here) or waiting on a Bun feature that doesn't exist today. This design accepts the two-invocation granularity CI already has (post sm-nrbu) rather than restructuring further.

**Additional blind spot found by independent review, accepted as residual**: Bun's coverage engine only instruments files actually loaded during the test run — three current files (`packages/catalog/src/catalogSource.ts`, `packages/catalog/src/installationRequirement.ts`, `packages/store/src/ToolMode.ts`) are pure type-only declarations with no runtime code, so they're harmlessly invisible to both the numerator and denominator today. The underlying mechanism is real, though: a *future* file with real logic that no test happens to import would sit at true 0% coverage forever while never being counted against the aggregate — a stronger failure mode than the invocation-level dilution risk already named below, since a diluted file is at least counted. Not solved by this design (Bun's per-invocation instrumentation model doesn't support otherwise), but partially complementary to Decision 1: a file with truly zero test-reachable imports is also likely to be flagged by knip's unused-export/unused-file detection, giving a second, independent check on the same blind spot rather than relying on coverage alone.

## Decision 3: Lint hygiene — `@eslint-community/eslint-plugin-eslint-comments`, not a bespoke rule

Package confirmed to exist on the registry (`bun info @eslint-community/eslint-plugin-eslint-comments` → real, latest `4.7.2`, MIT). Its `no-unlimited-disable` rule rejects a `/* eslint-disable <rule> */` with no matching `/* eslint-enable <rule> */` before end-of-file — this directly reproduces the sm-3u1c finding (`LayoutCanvas.tsx`'s file-wide disable, since fixed by hand) as an enforced rule. `require-description` rejects any `eslint-disable` comment lacking a `--` justification.

sm-lotm (unused-elsewhere-exported Props types in `apps/web/src/ui`) is **not** given a bespoke rule. It's a strict subset of what knip's "unused exports" / "unused exported types" detection (Decision 1) already covers — the ci-quality-gates change adding knip makes a second, narrower detector for the same finding class redundant. Verified directly: knip's live run above lists `CreateSpaceInput` (`apps/web/src/ui/spaceManager/CreateSpaceForm.ts`) and `WireframePolygon` (`apps/web/src/ui/wireframeScene.ts`) under "Unused exported types" — the same pattern class sm-lotm fixed elsewhere in the same tree, caught by the tool this design is already adopting.

Both new ESLint rules plug into the existing `eslint.config.ts` plugin-registration pattern already used for `eslint-plugin-import-x`, `eslint-plugin-functional`, etc. (top-of-file imports, `plugins: {}` block, per-scope rule entries) — no new mechanism, same file.

## Decision 4: Advisory-first rollout, per-gate flip trigger

All three gates ship non-blocking (visible in CI output, does not fail the job) initially, because the live runs above show each one has a non-trivial pre-existing backlog on this exact repo today. **Independent review (sm-mol-6n7t) found the naive version of this plan is mechanically broken for two of the three gates** — see "Advisory mechanism per gate" below for the fix, applied before describing each gate's specific backlog and flip trigger.

### Advisory mechanism per gate (how "non-blocking" is actually implemented)

The hole-poking pass found that "advisory" cannot mean "register the rule/threshold in the same already-strict, shared command and suppress its exit code," because two of the three gates share their invocation with a check that must stay blocking:

- **Knip**: genuinely standalone — it's a new, dedicated CI step with no other job depending on its exit code. `continue-on-error: true` on that step alone is sufficient; nothing else shares the invocation. No mechanism change needed here.
- **Coverage threshold**: `bun test packages ./.agents/hooks --coverage` / `bun --cwd apps/web test src --coverage` are the *same commands* the `test` job already runs to catch real test failures, and Bun gives no separate exit code for "a test failed" vs. "coverage missed its threshold" — `continue-on-error` on that step would silently swallow genuine test regressions for the whole advisory window, not just coverage misses. Fix: during the advisory period, do **not** set `bunfig.toml`'s `coverageThreshold` at all (so `bun test --coverage` keeps failing only on real test failures, exactly as it does today post-sm-wghm). Add a **separate, dedicated CI step** that parses the coverage report Bun already writes (`lcov` output via `--coverage-reporter=lcov`, or the text summary) and compares it against the threshold in a small script; only *this* step's exit code is suppressed (`continue-on-error: true`) during the advisory window. Flipping to blocking means adding `coverageThreshold` to `bunfig.toml` (making Bun itself the enforcer, folded back into the main `test` step) and retiring the separate script-based check.
- **Eslint-comments hygiene**: `bun run lint` runs `eslint . --max-warnings 0` — already zero-tolerance, so registering `no-unlimited-disable`/`require-description` directly in the shared `eslint.config.ts` ruleset that command enforces makes them blocking immediately, not advisory, regardless of any CI-level `continue-on-error`. Fix: during the advisory period, the two new rules run via a **second, separate ESLint invocation** scoped to only those two rules (e.g. a dedicated `eslint.config.advisory.ts` extending the base config, run as its own CI step with `continue-on-error: true`), not registered in the `eslint.config.ts` that the blocking `lint` script uses. Flipping to blocking means moving the two rules into the main `eslint.config.ts` and retiring the separate advisory config/step.

### Per-gate backlog and flip trigger

- **Dead-code (knip)**: 7 unused files, 2 unused deps, 7 unused devDeps, 35 unused exports, 24 unused exported types, 4 duplicate exports, *before* `knip.json` config work even removes the false positives (hooks, e2e fixture). Flip trigger: after `knip.json` is written (entry points + ignores for the known-dynamic cases) and every remaining real finding is either fixed or added to an explicit `knip.json` ignore list with a reason, flip the CI step from advisory to blocking (non-zero exit fails the job).
- **Coverage threshold**: given the mechanism above, this gate genuinely runs advisory (not "flip immediately" as originally planned — see Decision 2 for why the immediate-flip framing was also too aggressive on its own terms). Flip trigger: one week of CI runs on `main` with the separate advisory step showing zero threshold misses, confirming the buffer (widened per Decision 2) holds against normal churn, not just a single point-in-time measurement.
- **Eslint-comments hygiene**: needs a repo-wide fix-up of every existing `eslint-disable` comment lacking `eslint-enable` or a `--` reason. Independent review found this backlog is larger than originally described: **19** `eslint-disable-next-line` comments across 8 files (`BOMHeader.tsx`, `Toolbar.tsx`, `SpaceConstraint.ts`, `SpaceTemplate.ts`, `testing.ts`, `Point3D.ts`, `Point2D.ts`, `layoutSelectors.ts`, `useStore.ts`, `packer.ts`) lack a `--` reason, on top of the 3 already-fixed `LayoutCanvas.tsx` instances (sm-3u1c). Writing 19 individually-accurate justifications requires understanding each call site's reason for disabling a given rule — real content work, not a mechanical find-and-replace as originally characterized. Flip trigger unchanged: zero `no-unlimited-disable`/`require-description` violations on `main`, but the implementation bead should be scoped and estimated as a 19-site content pass, not a 3-site mechanical one.

Each gate's CI step reports its findings (dead-code list, coverage numbers, comment-hygiene violations) regardless of advisory/blocking state, so the backlog's shrinking is visible in every PR's CI output before the flip, not hidden until then.

### Forcing function: the flip is not automatic

Independent review found no mechanism actually forces re-evaluation of the flip-trigger conditions once each gate ships advisory — Decision 4 as originally written was prose intent only, and the one real precedent in this repo (`sm-wghm`, coverage-visibility-only, revisited within a day) worked because of sustained active work on epic `sm-rs0c`, not any automated check. If the epic closes or deprioritizes once these three gates ship advisory, nothing re-surfaces "did the backlog reach zero yet." This design's implementation tasks (filed after human-review, per this change's own ordering) MUST include a dedicated follow-up bead per gate — "flip `<gate>` to blocking once its backlog is zero" — created at advisory-rollout time, not left to be remembered informally.

## Risks / Trade-offs

- **knip false-positive maintenance burden**: `knip.json`'s entry/ignore list needs updating whenever a new Claude Code hook or Vite-aliased fixture is added — a config file that silently drifts out of date reintroduces exactly the "manual audit needed" problem this epic exists to solve. Not resolved by this design; independent review verified (by checking Storybook config, Playwright config, every `package.json` CLI script, and `.jules/prompts/`) that the known-false-positive list is complete for today's repo, but a future dynamic-resolution pattern would still need manual `knip.json` maintenance — flagged, not solved.
- **Coverage threshold granularity**: accepting invocation-level (not per-package) thresholds means a big coverage drop in one small, pure-functional package (e.g. `geometry`) could be offset by unrelated packages in the same invocation staying at 100%, without the gate catching it. Independent review quantified this with real numbers rather than leaving it abstract: `packages/store/src/layoutSelectors.ts` (real business logic) measures 49.60% line coverage in the apps/web invocation while that invocation's own aggregate reads 91.87% — nearly double, and the same file (`packages/assembly/src/PackingResult.ts`) reads 100%/100% under one invocation and 50%/54.05% under the other, because coverage here is a property of the invocation, not the file. Flagged, not solved — see Decision 2.
- **Bun's coverage numbers already show a real gap today**: `Dimensions2D.ts` and `Rect2D.ts` are at 0% function coverage right now (confirmed in the live run). The proposed thresholds are set to not fail on this pre-existing gap, which means the gate ships without actually closing it. That's a deliberate scope boundary (this design gates *regression*, not *today's baseline*) but worth flagging explicitly.
- **Advisory rollout had a mechanical incompatibility with two of the three gates** (found by independent review, remediated in Decision 4): coverage and eslint-comments hygiene each share their enforcement command with a check that must stay blocking (real test failures; the existing zero-tolerance `lint` script), so naively suppressing the shared command's exit code during the advisory window would have masked genuine regressions, not just new-gate noise. Decision 4 now runs each of those two gates through a separate, dedicated invocation during the advisory period specifically to avoid this.
- **No automated forcing function for the advisory-to-blocking flip** (found by independent review): the original design relied on continued attention to epic `sm-rs0c` rather than any mechanism. Decision 4 now requires a dedicated follow-up bead per gate, filed at advisory-rollout time.
- **No caching plan for knip, and its "runs in seconds" claim is a point-in-time measurement only**: confirmed accurate today (~1.4s locally) but unlike the ESLint step (which has a dedicated `actions/cache` entry), nothing keys a cache to `knip.json`/config hash, so the runtime assumption isn't verified against a larger future repo. Low priority given today's speed — revisit if runtime becomes a visible CI cost.

### Independent adversarial audit (sm-mol-6n7t, fresh-context subagent — completed)

An independent, fresh-context subagent (not the author of this design) ran the mandatory hole-poking pass required by the `feature-probe` formula before any implementation bead may be filed. It re-ran `bunx knip`, `bun test packages ./.agents/hooks --coverage`, and `bun --cwd apps/web test src --coverage` live against this repo (not just re-reading the design's claims), and grepped for `eslint-disable` comments directly.

Findings and how each was addressed above:

- **Critical** — advisory rollout as originally planned is mechanically incompatible with the coverage and eslint-comments gates: both share their enforcement command with a check that must stay blocking, so suppressing the shared command's exit code would mask real regressions, not just new-gate findings → closed: Decision 4 now runs each gate's advisory check through a separate, dedicated invocation, only folded into the shared blocking command at flip time.
- **High** — eslint-comments backlog undercounted: 19 undocumented `eslint-disable-next-line` comments across 8 files, not just the 3 already-fixed `LayoutCanvas.tsx` instances → closed: Decision 4 states the accurate count and reframes it as content work, not a mechanical pass.
- **High** — coverage buffer translates to ~2-5 functions of real headroom at this repo's scale, likely to trip on an ordinary small PR → closed: thresholds widened (Decision 2) from ~1.5-2 point margins to ~7-12 point margins; coverage also no longer flips to blocking immediately (Decision 4), giving a real verification window instead of shipping the tight buffer straight to blocking.
- **Medium** — coverage instrumentation only sees files a test happens to load, so a real-logic file with no test-reachable import sits at true 0% forever, invisible to both sides of the ratio → accepted residual risk, not solvable given Bun's per-invocation instrumentation model; noted as partially complementary to knip's unused-file detection (Decision 2).
- **Medium** — masking risk (invocation- vs. package-level granularity) confirmed with concrete numbers, more severe in magnitude than the original prose conveyed → risk text above updated with the measured figures (Decision 2 unchanged in mechanism, sharpened in description).
- **Medium** — no forcing function exists to make the advisory-to-blocking flip actually happen → closed: Decision 4 requires a dedicated follow-up bead per gate at advisory-rollout time.
- **Low** — `.agents/hooks/claude-hook.ts` framing conflated a shared helper with a true harness entry point → closed: Decision 1 corrected to name the 5 actual entry scripts; `claude-hook.ts` resolves transitively.
- **Low** — no caching plan for knip, "scales fine" claim is point-in-time only → accepted, flagged as low-priority, not blocking.

The auditor also confirmed several claims hold up under direct re-verification, not just re-reading: all of knip's reported numbers (7 unused files, 2 unused deps, 7 unused devDeps, 35 unused exports, 24 unused exported types, 4 duplicate exports) and both coverage baselines (91.67%/97.41% packages+hooks, 86.33%/91.87% web) reproduced exactly; the known-false-positive list for knip is complete against today's repo (checked Storybook/Playwright config, every CLI script, `.jules/prompts/`); and wiring knip inside the existing `lint` job (rather than a new job) was confirmed as the right call, since it means the eventual blocking flip inherits `lint`'s already-required branch-protection status with no separate ruleset change needed.

## Open Questions

- Should the dead-code step run on every PR or only on `main`-target PRs that touch source files (to avoid re-running a whole-repo scan on doc-only changes)? Leaning toward: every PR, since knip's runtime on this repo is a few seconds — not worth the conditional-execution complexity. Independent review confirmed the runtime assumption holds today (locally); CI-specific runtime and caching remain unverified (see Risks) and are left to the implementation bead.
- `@fission-ai/openspec`, `prettier-plugin-packagejson`, `modern-web-guidance` all show as unused by both knip and depcheck (CLI-only tooling, per AGENTS.md's existing carve-out) — should `knip.json` ignore them by name, or should knip's own `ignoreDependencies` pattern be scoped more generally to "anything AGENTS.md's Agent Tooling Packages section lists"? Left to the implementation bead.
- Exact CI wiring (job/step YAML) for the two decoupled advisory checks (coverage-threshold script, advisory-only ESLint config) introduced in Decision 4 is left to the implementation bead, not this design.
